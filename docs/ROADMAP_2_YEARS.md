# Two-year direction

Status: **RESEARCH DIRECTION**. This is a sequence of evidence-gated possibilities, not a release schedule, support promise, or commitment to build every named engine. Years describe broad stages from Genesis, not fixed calendar deadlines.

## Foundation / Year 0

Genesis establishes the recovery laws, proposed evidence/health/cause/state contracts, risk and authorization boundaries, project relationships, case-study discipline, mission protocol, and repository foundation. It does not implement recovery capabilities.

The first bounded architectural experiment should use fictional software and synthetic evidence to separate symptoms, multiple causes, healthy state, unknowns, ordering, and verification. The sole current task and its acceptance criteria belong in [progress](PROGRESS.md).

**Exit evidence:** the documents agree on the important terms; a small human-readable synthetic case can expose ambiguity without any live probes or mutations. Unresolved questions become explicit decisions or research limits rather than speculative implementation.

## Year 1: prove a small recovery reasoning path

Possible blocks, each requiring a real need and its own acceptance criteria:

- Refine a minimal versioned evidence/report contract using synthetic cases and a real read-only consumer.
- Implement a small pure rule evaluator that preserves unknowns, applicability, provenance, and multi-cause findings.
- Add one narrowly supported observation adapter after a real incident defines what it must observe.
- Explore dependency and capability requirements for that same incident; avoid a universal inventory project.
- Compare scoped sanitized snapshots, distinguishing machine changes from changes in knowledge.
- Create human-readable explanations and machine reports with shared semantic verification.
- Investigate a read-only CWRE contract mapping, retaining CWRE independence and unsupported-state handling.
- Only after these boundaries hold, consider one authorized repair workflow with backup, minimal mutation, fresh verification, and a demonstrated return or safe-stop path.

**Exit evidence:** repeatable synthetic tests, negative cases, bounded adapter behavior, explicit supported scope, and verification of one selected end-to-end case. A passed test suite does not imply universal recovery support.

## Year 2: expand by proven incidents

Possible directions include migration profiles, reusable case/rule promotion, richer causal and capability graphs, durable recovery journals, and repair-specific rollback verification. Additional runtime, service, container, database, GPU, or operating-system adapters require actual incidents and tests; the list is not a backlog to implement mechanically.

Integration research may explore HAAEP recovery playgrounds, ARX evidence exchange, and Dragon-Hydra recovery constraints. These projects retain their own contracts and authority boundaries. A new human surface should consume the existing semantics instead of duplicating recovery logic.

If executable distribution becomes justified, provenance, signing, reproducible verification, update policy, and recovery from failed updates need deliberate development blocks. Genesis establishes none of these facilities. Broader packaging or extension support must not introduce unrestricted code execution or inherited repair authority.

**Exit evidence:** each added capability has a supported scope, independent verification, safe failure behavior, human explanation, and a maintained regression case. Platform expansion occurs only when environment evidence and ownership of long-term maintenance exist.

## Admission and stop rules

Before a new engine or adapter is admitted, identify the incident or consumer, current evidence, smallest coherent capability, required authority, preserved healthy state, and verification method. A detection-only feature does not need a speculative mutation subsystem.

Stop or narrow a block when provenance is insufficient, outcomes cannot be verified, recovery promises exceed what can be demonstrated, or a reusable abstraction is unsupported by a second real requirement. Preserve the evidence and useful learning from an inconclusive experiment.

Progress is measured by correct diagnoses, avoided false claims, healthy state preserved, scoped repairs verified, and useful knowledge retained. Module count and apparent breadth are not success metrics.
